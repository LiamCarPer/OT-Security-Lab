## 2. PT-01: PowerShell Modbus write

The PowerShell workstation sits in L2 because conduit **C1** permits
Supervisory → Control Modbus/502, while **C5** denies the L3 EWS Modbus access.
A normal `TcpClient` write from the EWS would never produce a Modbus PDU.

The scenario:

1. Read the intake process image (`FC3`, HR0–HR6).
2. Write `42` to HR1 (intake pump speed) with `FC6`.
3. Read the value back.
4. Restore the original value.

Observed result: the write and restore were acknowledged by PLC-01, and the
gateway raised `UNAUTHORIZED_MODBUS_WRITE` with `source_ip=172.22.0.30`. The
register is not used by the ST logic, so the process state was unchanged.

**Finding PT-01-F1 — C1 is zone-wide, not source-restricted.** The firewall
permits any Supervisory host to reach Modbus/502; the detector's source
allow-list (HMI and EWS) is the behaviour control. That is a deliberate
defence-in-depth gap for this exercise and is tracked as **RD-15**: restrict C1
to approved Modbus masters.

**Finding PT-01-F2 — PowerShell Sigma is not live-validated.** The
`powershell_ot_modbus_client.yml` rule targets Windows 4104 Script Block
Logging. The lab's PowerShell host is PowerShell 7 on Linux, so the rule is
statically validated in CI but has no live Windows telemetry source. This is
recorded in `CLAIMS.md` and is the reason RD-15 includes a Windows EDR
endpoint.

## 3. PT-02: OT service-port scan

`nmap -Pn -n -T4 --max-retries 1 --host-timeout 15s -p 502,102,20000,4840
172.21.0.10-12` from the Enterprise adversary host.

Observed result: the firewall filtered the probes, the gateway observed the
SYNs and `OT_PORT_SCAN` fired with `source_ip=172.24.0.10`,
`dest_ports=102,502,20000`, `port_count=3`.

**Finding PT-02-F1 — the old rules did not see a SYN scan.** The existing
`OT_BRUTE_FORCE_SCAN` rule only counts Modbus exception responses; an nmap SYN
scan produces no Modbus PDU. The new stateful `ot_port_scan.py` rule closes the
gap. A 300-second per-source cooldown prevents one scan from flooding the alert
stream.

## 4. PT-03: Caldera operation

The `OT External Adversary` profile runs four abilities in order:

1. OT Service Discovery (T0846)
2. Unauthorized Modbus Write (T0831)
3. OT Lateral Movement (T0886)
4. Process Safety Interlock Stimulus (T0836)

The operation is reproducible with:

```bash
make caldera-image
make caldera
export CALDERA_API_KEY=ot-lab-caldera-api
pwsh -File powershell/Invoke-OTCalderaOperation.ps1 \
    -AdversaryName 'OT External Adversary' \
    -EvidencePath evidence/caldera_operation.json
```

The recorded operation is `77e7ca6a-88f3-41b9-8ca6-9e7b9ae1feee`: it reached
`finished`, all four links completed with status `0`, and the evidence file
contains the link results plus the Loki alert summary. The deterministic
compliance gate remains the regression test; Caldera is the platform-level
orchestration demonstration.

A second operation was stopped during the exercise because the Sandcat agent
stopped checking in after the third ability. The first complete operation is
the recorded evidence; the agent-liveness issue is an operational note for the
next cycle (add an agent-health check to the workflow, not just a startup
wait).
